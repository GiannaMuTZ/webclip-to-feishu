# 首次验收与测试记录

## 已覆盖的自动化验证

运行 `npm run check`。测试在本机使用临时 HTTP 端口；不需要飞书凭据。仓库的 GitHub Actions 会使用同样命令，在 Node.js 22 和 24 执行。

- KaTeX 渲染双层 DOM 只产生一个公式；MathJax 脚本、MathItem 属性和辅助 MathML 能恢复源码。
- `\(...\)`、`\[...\]`、美元分隔符、代码和货币文本分开处理。
- 表格的合并区域、单元格位置与公式正确；大表格分片不丢失跨界内容。
- 飞书请求创建文档、表格骨架、填充单元格、合并区域的顺序正确。
- 原生 equation、链接编码、文本分批、emoji 完整性得到检查。
- 恶意页面 HTML、脚本链接、表单字段、无效来源、Host 和凭据得到检查。
- token 缓存、明确拒绝后刷新、429 重试、网络错误不盲目重试得到检查。
- 同一任务去重、部分失败文档链接、重启不重复写入得到检查。
- 同一张表格的多个合并区域分开更新；每个批量更新请求中的 Block ID 保持唯一。

## 2026-10-24 真实租户联调结果

环境：macOS、Chrome 本地扩展、Node.js 24、飞书中国版企业自建应用。应用身份仅开通 `docx:document:create` 和 `docx:document:write_only`，机器人是新建收藏文件夹的可编辑协作者。

- `npm run check`：42 项测试通过，包含真实本机 HTTP 集成测试。
- 从 Chrome 扩展捕获本地 `demo.html`，预览得到 19 个内容块、7 个公式、1 张表格；真实保存成功。
- 在飞书中目视核对行内质能公式、独立估计式、积分、分数和基础 MathML，均正常渲染。双击质能公式能打开包含 `E = mc^2` 的源码编辑框。
- 表格为 4 行、3 列；「模型」跨 2 行，「估计结果」跨 2 列；两个系数公式正常显示。将标准误单元格 `0.08` 编辑为 `0.080` 后撤销，恢复原值。
- 来源链接、代码、`$variable`、`$5`、`$10` 均保留。
- 保存期间关闭扩展弹窗，重新打开后恢复任务成功状态及文档链接。

首次联调发现同一张表格的两个合并操作共用一个 `batch_update` 请求时，飞书返回 `1770001`。官方接口要求同批次 Block ID 不重复；现改为逐个合并区域提交，并补充回归测试，重试后完整导入成功。参见 [官方 SDK 中的批量更新约束](https://pkg.go.dev/github.com/larksuite/oapi-sdk-go/v3@v3.12.0/service/docx/v1#BatchUpdateDocumentBlockReqBody)。

飞书会采用自己的字体、列宽和段落间距；此轮验证的是内容、原生可编辑元素及合并关系。真实账号的文档链接和密钥不写入公开仓库。

2026-10-26 补测：在 Chrome 中仅选中示例的合并表格，使用「选中内容」提取。预览得到 1 个内容块、2 个公式、1 张表格，没有带入前后正文；实际保存到飞书成功。

## 飞书端真实验收（配置完成后执行）

自动化测试中的飞书请求使用模拟接口；以下是首次接入真实账号时必须做的检查，不能以本地预览代替。

1. 启动服务并加载扩展，打开本地 demo 页面。
2. 智能正文模式提取；确认标题、正文、公式和合并表格在预览中存在。
3. 点击保存，确认出现成功状态和飞书文档链接。
4. 在飞书中核对 `E=mc^2`、矩阵估计式、积分式和基础 MathML 的显示；点击公式能编辑。
5. 核对表格为 4 行 3 列、第一列表头跨 2 行、结果表头跨 2 列，且表格内的两个系数公式可编辑。
6. 核对代码缩进、`$variable`、`$5` 和 `$10` 原样保留，来源链接正确。
7. 用选区模式只保存中间一个段落及表格，确认未带入其余正文。
8. 选择一篇真实网页文章（尤其包含公式和表格的目标网站）重复测试。
9. 保存较长文章时关闭扩展弹窗，重新打开确认能继续显示任务进度。

验收时记录目标站点、飞书租户配置、公式渲染差异和表格差异，便于后续增加针对性兼容。不同网站的内容结构与飞书公式引擎版本可能不同。
